그다음 작성자가 개념 명세를 준비합니다. 에이전트에게 기술 주제만 던지기보다 구성 요소, 입력과 출력, 수치의 의미, 상태 변화, 생략할 내용, 사용할 독자층을 함께 제공합니다. 예컨대 요청 제한을 표현한다면 허용량과 시간 구간이 무엇을 뜻하는지, 초과 요청이 거절되는지 대기하는지처럼 설명할 동작을 먼저 명시합니다. 구체적인 수치가 검증되지 않았다면 임의의 값을 사실처럼 표시하지 말고, 설명용 예시임을 화면에 드러내야 합니다.

첫 생성물은 프로토타입으로 취급합니다. 기능을 최소화해 구성 요소가 서로 연결되는지, 사용자가 어떤 조작을 할 수 있는지, 조작 전후에 수치와 설명이 일치하는지 확인합니다. 움직임이 개념을 더 잘 설명하는지 검토하고, 효과가 이해를 방해하면 제거합니다. 이후 실제 배포 형식으로 내보내 로컬 빌드 또는 지정된 브라우저에서 확인합니다. 소개된 스크린샷 검사는 시각적 비교의 출발점으로 삼을 수 있지만, 핵심 동작은 직접 재현해 확인해야 합니다.

적용 조건은 세 가지입니다. 설명할 원리와 수치가 담당자에게 확인돼 있을 것, 산출물을 볼 대상과 배포 위치가 정해져 있을 것, 인터랙션을 점검할 시간과 담당자가 있을 것입니다. 반대로 개념 정의가 아직 논쟁 중이거나, 보안·운영 정책을 다루면서 예시와 실제 동작을 분리하기 어렵거나, 지원 브라우저와 접근성 요건을 확인할 수 없다면 공개용 제작을 미루는 편이 좋습니다.

- [ ] 예시 값과 실제 운영 값이 화면에서 구별되도록 정한다.
- [ ] 독자, 배포 위치, 출력 형식(SVG·독립 HTML·React/Next.js)을 선택한다.
- [ ] 에이전트에 시각 효과보다 개념의 정확성과 불필요한 장식의 제한을 우선 요청한다.

- [ ] 기술 검토자가 승인하기 전에는 최종 문서나 외부 페이지에 배포하지 않는다.
