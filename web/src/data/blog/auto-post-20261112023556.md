## 실무 판단

첫 번째 판단 기준은 자동화 가능성보다 실패 비용입니다. 모바일 에이전트는 화면을 보고 조작하므로 앱 개편, 팝업, 로그인 만료, 네트워크 지연에 따라 같은 요청도 다른 결과를 낼 수 있습니다. 조회 내용을 정리하거나 전송 전 초안을 만드는 일은 실패를 발견하고 되돌리기 쉽지만, 결제·게시·삭제·권한 변경은 작은 오조작도 실제 손실로 이어질 수 있습니다. 따라서 초기에 자동화할 업무는 결과를 사람이 확인할 수 있고, 실행을 취소하거나 다시 처리할 수 있는 것으로 한정하는 편이 합리적입니다.

두 번째는 데이터 경로입니다. 자체 서버가 없다는 설명은 중간 서버를 통한 처리를 줄이는 데 참고가 되지만, 화면 정보가 모델 제공사로 전달된다는 설명과 함께 읽어야 합니다. 화면에 고객 이름, 내부 메모, 인증 정보가 보이면 자동화 과정에서 해당 정보가 모델 입력에 포함될 가능성을 검토해야 합니다. 조직의 데이터 분류·외부 전송 정책과 선택한 모델 제공사의 조건을 확인하지 않은 채 업무용 계정으로 연결하는 것은 피해야 합니다.

세 번째는 사람 확인의 범위입니다. 결제나 보안 설정 변경에 확인 단계가 있다는 안내는 유용한 설계 신호지만, 모든 위험한 작업이 빠짐없이 감지된다는 의미는 아닙니다. 실무 적용 시에는 도구의 기본 확인 기능에만 의존하지 말고, 업무 절차 자체에 승인과 최종 검토를 남겨야 합니다. 특히 여러 앱을 이동하는 작업에서는 한 화면에서 보이는 결과만 확인하지 말고, 최종 상태가 저장됐는지도 별도로 확인해야 합니다.

마지막으로, 자체 벤치마크의 점수는 도입 여부를 결정하는 지표가 아니라 시험할 이유를 제공하는 자료입니다. 업무에 중요한 것은 평균 점수보다 지정한 과업을 끝까지 완료하는지, 잘못된 입력을 알아차리는지, 실패 후 안전하게 멈추는지입니다. 성공·실패를 같은 기준으로 기록하고, 수동 처리와 비교해야 실제 절감 효과를 판단할 수 있습니다.

## 업무에 어떻게 쓸까

다음 절차는 도입 전 소규모 검증을 위한 권고입니다. 실제 앱에서 사용하기 전에 먼저 조직 정책과 기기 보안 기준을 확인하십시오.

1. **후보 업무를 하나 고릅니다.** 매일 반복되지만 결과가 단순하고, 데이터 민감도가 낮은 조회나 입력을 선택합니다. 예를 들어 공개 정보 확인, 테스트 계정에서의 폼 입력처럼 실수의 영향이 제한된 작업이 적절합니다. 처음부터 사내 메신저 발송, 고객 데이터 수정, 구매·결제 업무를 시험 대상으로 삼지 않습니다.
2. **성공 조건과 금지 동작을 정합니다.** 성공은 화면 이동 횟수가 아니라 업무 결과로 정의합니다. 예를 들어 지정한 항목이 정확히 입력됐고, 제출 버튼은 누르지 않은 상태처럼 확인 가능한 조건으로 씁니다. 금지 동작에는 실제 제출, 삭제, 결제, 보안 설정 변경, 비밀번호 입력을 명시합니다.
3. **시험 환경을 분리합니다.** 가능하면 테스트 계정과 비민감한 데이터로 먼저 실행합니다. APK 설치 전에는 저장소와 릴리스 정보를 확인하고, 접근성 권한을 어떤 범위로 허용하는지 살펴봅니다. 권한의 의미나 설치 파일의 출처를 확인할 수 없다면 시험을 중단합니다.
4. **사람이 화면을 보며 한 번씩 확인합니다.** 요청을 짧고 구체적으로 주고, 에이전트가 화면을 어떻게 해석했는지와 각 단계의 결과를 관찰합니다. 팝업이 예상과 다르거나 앱 화면이 바뀌었을 때 계속 진행하는지 확인합니다. 작업이 끝난 뒤에는 앱의 실제 저장 상태를 수동으로 검증합니다.
5. **기록을 남기고 확대 여부를 결정합니다.** 아래 항목을 최소한의 시험 기록으로 사용할 수 있습니다.

| 기록 항목 | 확인할 내용 |
|---|---|
| 과업·앱 | 어떤 화면에서 어떤 결과를 만들려 했는가 |
| 성공 조건 | 완료 여부를 사람이 판정할 기준은 무엇인가 |
| 결과 | 성공, 부분 성공, 실패 중 무엇인가 |
| 오류·복구 | 잘못된 탭이나 멈춤을 알아차리고 복구했는가 |
| 데이터·권한 | 화면에 민감정보가 있었는가, 어떤 권한을 허용했는가 |
| 다음 결정 | 같은 조건으로 재시험, 범위 축소, 중단 중 무엇인가 |

반복 시험에서 정확도와 복구 가능성이 업무 기준을 만족하고, 데이터 전송이 정책에 부합할 때만 범위를 조금씩 넓힙니다. 성공률이 낮거나 실패했을 때 예상하지 못한 제출·변경이 발생하면 해당 과업은 중단하고 수동 처리로 되돌립니다.
