## 실무 판단

이 사례에서 읽을 핵심은 AI가 코드를 작성하는 속도와 사람이 결과를 검토하는 속도가 다를 수 있다는 점입니다. 생성량이 늘어도 설계 의도, 오류 처리, 의존 관계를 설명할 수 없다면 변경을 받아들이는 데 드는 비용이 커집니다. 특히 취미 프로젝트처럼 “나중에 정리하면 된다”고 미루기 쉬운 작업은, 작은 부채가 누적돼 재검토 시점을 넘길 수 있습니다. 이는 저자의 경험에서 도출한 편집부의 해석이지, 모든 AI 생성 코드에 해당한다고 단정할 수는 없습니다.

또 하나는 요구사항의 우선순위입니다. AMP의 출발점은 오프라인 재생과 불편한 가사 표시였지만, 개발 목표에는 언어 선택, 의존성, 시스템 통합, UI 구현도 포함됐습니다. 요구가 늘어나는 상황에서 AI에게 전체 애플리케이션을 한 번에 맡기면, 기능 구현과 설계 결정이 한꺼번에 섞일 수 있습니다. 그러면 무엇을 왜 만들었는지 추적하기 어려워질 수 있으므로, 요구사항을 사용자 기능과 기술 선택으로 나눠 검토하는 게 유용합니다.

이 판단이 모든 프로젝트에서 직접 재작성해야 한다는 뜻은 아닙니다. 오히려 기준은 “AI가 썼는가”가 아니라 “변경의 범위와 근거를 검증할 수 있는가”여야 합니다. 이미 있는 코드와의 호환성, 실패 시 복구 방법, 테스트 가능성을 확인할 수 있다면 AI를 보조 도구로 계속 쓸 수 있습니다. 반대로 핵심 로직이 한 번에 대량 변경되거나, 작성자도 설명하지 못하는 코드가 쌓인다면 다음 기능 추가보다 범위 축소와 정리가 우선입니다.

## 업무에 어떻게 쓸까

작은 기능 하나를 AI에 맡기는 실험부터 시작할 수 있습니다. 예를 들어 “음악 재생 기능 전체를 만들어줘” 대신 “선택한 파일의 재생·일시정지 상태를 처리하는 함수만 제안해줘. 기존 인터페이스는 바꾸지 말고, 오류 상황과 테스트 방법도 함께 적어줘”처럼 요청 범위를 제한합니다. 음악 플레이어의 예시는 설명을 위한 것이며, 실제 업무에서는 로그 파서의 한 단계, 화면의 한 입력 검증처럼 결과를 독립적으로 확인할 수 있는 작업으로 바꾸면 됩니다.

**적용 조건**은 입력과 출력, 수정 허용 범위, 확인 방법을 사람이 먼저 정할 수 있을 때입니다. **중단 조건**은 요구하지 않은 파일까지 바꾸거나, 의존성 추가 이유를 설명하지 못하거나, 테스트가 실패했는데도 원인을 좁히지 못할 때입니다. 이런 상황에서는 프롬프트를 더 길게 쓰기보다 변경을 되돌리고 작업을 더 작게 나누는 편이 안전합니다.

한 번의 작업은 다음 순서로 진행합니다.

1. 현재 동작과 변경할 문제를 한 문장씩 적습니다. 예: “재생 중인 곡을 일시정지해도 선택된 곡은 유지한다.”
2. 수정할 파일이나 모듈의 범위를 정하고, 변경하지 말아야 할 인터페이스를 명시합니다.
3. AI에 구현을 요청하되, 수정 이유와 실패 상황, 확인할 테스트를 함께 제시하게 합니다.
4. 생성된 코드를 바로 합치지 말고 변경 내역을 확인합니다. 요청하지 않은 기능, 큰 구조 변경, 새 의존성이 있는지 살핍니다.
5. 기존 테스트와 새 테스트를 실행하고, 실제 업무 환경에서 중요한 실패 조건을 사람이 확인합니다.
6. 근거를 설명할 수 없는 부분은 보류하거나 작게 다시 요청합니다. 검토 가능한 상태가 된 뒤에만 다음 기능으로 넘어갑니다.

아래 요청 양식은 팀의 코드 작업에 맞게 복사해 조정할 수 있습니다.

> **목표:** [사용자에게 보이는 동작 한 가지]
> **현재 동작:** [확인된 상태]
> **허용 범위:** [수정 가능한 파일·함수]
> **변경 금지:** [유지해야 할 API·데이터 형식·의존성]
> **완료 기준:** [재현 가능한 테스트 또는 확인 절차]
> **응답에 포함할 것:** 변경 요약, 실패 가능성, 추가한 의존성의 이유, 사람이 확인해야 할 부분
> **중단 조건:** 범위 밖 수정이나 완료 기준을 검증할 수 없는 변경이 필요하면 코드를 작성하기 전에 질문할 것

이 양식의 목적은 AI에게 일을 더 많이 시키는 것이 아니라, 결과를 수용할 기준을 먼저 고정하는 데 있습니다. 테스트가 없거나 검증 환경이 준비되지 않았다면, 코드 생성보다 먼저 최소한의 수동 확인 절차를 정의해야 합니다.

## 실행 체크리스트

- [ ] 요청을 기능 하나 또는 독립적으로 확인 가능한 변경 하나로 줄였는가?
- [ ] 수정 허용 범위와 건드리면 안 되는 인터페이스를 적었는가?
- [ ] “완료”를 판단할 테스트나 재현 절차가 있는가?
- [ ] 생성 결과가 요청하지 않은 파일·기능·의존성을 추가하지 않았는가?
- [ ] 실패 처리와 오류 상황을 사람이 확인했는가?
- [ ] 변경 내용을 다른 개발자에게 설명할 수 있는가?
- [ ] 설명이나 검증이 어려운 부분을 합치지 않고 보류할 기준이 있는가?

체크 항목이 여러 개 비어 있다면 AI 사용을 중단할 필요까지는 없습니다. 다만 다음 프롬프트를 넣기 전에 요청 범위, 테스트, 검토 책임자를 먼저 정하는 것이 좋습니다. 특히 핵심 로직을 여러 파일에 걸쳐 바꾸는 작업은 기능을 분할해 각각 검토하고, 변경 간 연결은 별도 작업으로 확인합니다.
