둘째, 장기 실행은 단순히 작업 시간을 늘리는 기능이 아니라 감독 방식을 바꾸는 선택입니다. 짧은 코드 수정은 변경 내용을 곧바로 읽고 시험하기 쉽지만, 몇 시간 이상 이어지는 작업은 중간에 어떤 파일을 바꾸고 어떤 도구를 호출했는지 확인하기 어려워질 수 있습니다. 작업을 잘게 나누고 중간 산출물을 남기게 해야 결과의 검토 비용을 관리할 수 있습니다.

셋째, “목표 중심 지시”는 목표와 제약을 생략하라는 뜻이 아닙니다. 구현 목표는 간단히 적더라도 변경 금지 영역, 테스트 기준, 외부 시스템에 영향을 주는 행동, 멈춰야 할 조건은 명시하는 편이 낫습니다. 요약에 언급된 동료 확인과 배포 단계는 자동화의 끝이 아니라 사람의 승인선을 둘 수 있는 지점으로 해석할 수 있습니다.

넷째, 여러 인터페이스와 플러그인을 연결하면 정보가 오가는 경로도 늘어납니다. 편의성이 업무 적용의 근거가 되려면, 어떤 계정이 어떤 자료를 읽고 어떤 작업을 실행하는지 먼저 확인해야 합니다. 특히 개발 저장소와 메신저·문서 도구를 한 흐름으로 연결할 때는 접근 권한을 기능별로 나누고, 시험 계정이나 제한된 자료로 시작하는 것이 현실적인 접근입니다.

## 업무에 어떻게 쓸까

가장 적합한 첫 시도는 입력 자료가 정해져 있고, 결과를 사람이 쉽게 확인할 수 있는 반복 작업입니다. 예를 들면 저장소의 변경 사항을 규칙과 테스트에 맞춰 검토하거나, 내부 문서 묶음에서 주간 보고 초안을 만드는 일입니다. 반대로 고객 데이터 삭제, 운영 배포, 권한 변경처럼 오류의 영향이 크고 복구가 어려운 업무는 초기 시험 대상에서 제외하십시오.

1. **작업 하나를 고릅니다.** 한두 문장으로 결과물을 설명할 수 있고, 완료 여부를 테스트나 검토 기준으로 판정할 수 있는 작업을 택합니다. “서비스를 개선해 달라” 대신 “이 폴더의 변경에서 관련 테스트를 실행하고 실패 원인과 수정 제안을 보고하라”처럼 범위를 줄입니다.
2. **필요한 맥락을 모읍니다.** 저장소 규칙, 참조 문서, 디자인 기준 중 이번 작업에 필요한 것만 지정합니다. 자료마다 최신 여부와 담당자를 확인하고, 불필요한 개인정보나 비밀 정보는 입력 경로에서 제외합니다.
3. **권한과 산출물을 제한합니다.** 처음에는 읽기·분석·초안 작성부터 시작하고, 수정이 필요하다면 작업 브랜치나 복사본에서만 허용합니다. 변경 파일 목록, 실행한 검사, 발견한 불확실성을 결과에 포함하도록 요청합니다.
4. **작은 작업으로 검증합니다.** 결과의 정확성뿐 아니라 에이전트가 엉뚱한 자료를 읽지 않았는지, 지시 밖의 변경을 하지 않았는지도 봅니다. 사람이 수정한 부분과 에이전트가 만든 부분을 구분할 수 있게 기록을 남깁니다.
5. **검토 통과 뒤에만 범위를 넓힙니다.** 반복 작업에서 수정률과 검토 시간을 확인하고, 안정성이 확인된 경우에만 도구 연결이나 장기 실행을 추가합니다. 배포·공유·외부 메시지 전송은 별도 승인 단계로 둡니다.

슬라이드나 보고서 생성에도 같은 원칙을 적용할 수 있습니다. 먼저 자료 목록과 핵심 주장을 뽑게 하고, 사람이 아웃라인과 근거를 승인한 다음 파일을 만들게 하십시오. 생성된 문장이 자료에서 확인되지 않으면 빈칸을 임의로 채우지 말고 “검증 필요”로 남기도록 하는 것이 안전합니다. 이러한 단계형 작성과 렌더링 검토는 슬라이드 가이드가 제시한 흐름과도 맞닿아 있습니다. [슬라이드 작업 가이드](https://reapi.ai/ko/blog/how-to-use-codex-to-generate-slides)
