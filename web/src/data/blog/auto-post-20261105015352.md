## 실무 판단

sutura의 실무적 의미는 “AI가 SQL을 더 잘 쓰게 한다”라기보다 “AI가 질문할 수 있는 분석 언어를 조직의 정의로 제한한다”는 데 있습니다. SQL 생성의 품질만 높여도 지표가 팀마다 다르면 숫자는 일치하지 않습니다. 반대로 지표 정의가 명확하고 시스템에 등록돼 있다면, 자연어 질의를 대시보드와 같은 기준으로 처리할 가능성을 시험할 수 있습니다. 이는 제품 소개에서 확인된 동작을 바탕으로 한 편집부의 해석이며, 실제 결과의 정확도를 보장한다는 뜻은 아닙니다.

따라서 첫 도입 관문은 모델 선택보다 지표 카탈로그의 준비 상태입니다. 매출, 활성 사용자, 전환율처럼 보고에 자주 쓰는 지표마다 계산식, 단위, 기간 기준, 필수 조인, 허용 가능한 분류를 설명할 수 있어야 합니다. “매출”이 주문액인지 결제액인지 환불 반영액인지 불분명하다면, 에이전트의 응답을 검증하기 어렵습니다. 이때 필요한 일은 프롬프트를 다듬는 것보다 정의를 합의하고 카탈로그에 반영하는 것입니다.

두 번째 관문은 권한이 실제 실행 주체에 맞게 작동하는지입니다. 소개 자료는 권한과 행 수준 정책, 마스킹을 데이터 시스템이 적용한다고 설명합니다. 따라서 엔진의 요청 거절 기능만으로 접근 통제가 완성된다고 보기는 어렵습니다. 서비스 계정으로 실행하는 구성이라면 그 계정이 볼 수 있는 데이터 범위가 사용자별 업무 범위와 일치하는지 따로 확인해야 합니다. 호출자별 신원 지원 여부도 데이터 소스에 따라 차이가 있으므로, 연결 대상별로 검증해야 합니다.

세 번째 관문은 결과를 다시 설명할 수 있는지입니다. 정의 버전과 해시를 결과에 포함한다는 설명은 계산 기준의 추적 가능성을 높일 수 있는 설계로 읽힙니다. 다만 버전 정보만으로 데이터 시점, 원천 데이터 변경, SQL 실행 결과까지 전부 재현된다고 단정할 수는 없습니다. 결과를 의사결정 자료에 사용할 계획이라면 기준 시각, 질의 조건, 데이터 원천도 함께 기록하는 절차가 필요한지 검토해야 합니다.

## 업무에 어떻게 쓸까

가장 현실적인 시작점은 반복되는 내부 질의 하나를 골라, 답변 생성보다 “같은 질문에 같은 기준으로 답하는가”를 확인하는 것입니다.

1. **질문을 좁힙니다.** 예를 들어 월간 매출처럼 이미 보고서에서 쓰는 지표를 고릅니다. 지역·제품군 등 분류 기준도 기존 대시보드에서 허용한 범위로 한정합니다.
2. **정의를 대조합니다.** 지표의 계산식, 기간 기준, 조인 관계, 제외 조건을 담당자와 확인합니다. 표현이 모호하거나 보고서마다 정의가 다르면 시험을 시작하기 전에 그 차이를 기록합니다.
3. **카탈로그와 연결 대상을 정합니다.** 현재 조직에서 관리하는 정의를 어디에 둘지 확인하고, 시험용 데이터 소스와 실행 신원을 정합니다. 처음부터 여러 소스를 결합하기보다 단일 소스의 읽기 전용 질의로 범위를 제한하는 편이 원인 파악에 유리합니다.
4. **기준 결과와 비교합니다.** 같은 조건의 대시보드 또는 검증된 쿼리 결과를 기준으로 삼습니다. 기간 경계, 필터, 분류별 합계가 맞는지 확인하고, 숫자가 다르면 모델의 답변 문구보다 지표 정의와 생성 SQL, 원천 데이터를 먼저 점검합니다.
5. **거절 동작도 시험합니다.** 지표에 없는 분류 기준, 권한이 없는 데이터, 허용되지 않은 요청을 넣어 시스템이 실행하지 않고 사유를 명확히 반환하는지 확인합니다.
6. **업무 영향에 맞춰 확대합니다.** 비교 결과와 접근 통제가 확인된 뒤에만 사용자나 지표 범위를 넓힙니다. 재무 보고, 인사 데이터 등 오류나 과도한 노출의 영향이 큰 영역은 별도 검토와 승인 없이 자동화 범위에 포함하지 않습니다.

적용 조건은 최소한 지표 소유자, 검증 가능한 기준 결과, 읽기 범위가 제한된 실행 신원을 확보하는 것입니다. 반대로 지표 정의가 서로 충돌하거나, 질의 권한을 사용자 업무에 맞춰 제한할 수 없거나, 결과 차이를 조사할 로그와 담당자가 없다면 시험을 중단하고 데이터 거버넌스부터 정비하는 편이 낫습니다.

## 한계와 주의점

권한과 정책을 데이터 시스템이 적용한다는 설명은 중요하지만, 조직의 실제 설정이 올바르다는 보증은 아닙니다. 호출자별 신원 지원이 소스마다 다르다는 설명도 있으므로, 서비스 계정이 사용되는 경로의 데이터 접근 범위와 감사 로그를 별도로 검증해야 합니다. 캐시를 두지 않는다는 설명 역시 그 자체로 모든 계층의 캐시나 데이터 보관 정책이 없다는 뜻은 아닙니다.

또한 허용된 자료만으로는 실제 구현의 상세 설정, 지원 버전과 제한, 운영·모니터링 기능, 장애 시 동작, 민감 데이터 처리 조건을 확인할 수 없습니다. 도입 전에는 저장소의 문서와 라이선스, 보안 검토 자료, 데이터 소스별 권한 동작을 직접 확인해야 합니다. 결론적으로 sutura는 의미가 정리된 지표를 에이전트 질의에 연결하려는 선택지로 검토할 수 있지만, 먼저 해결해야 할 과제는 SQL 생성보다 조직의 지표 정의와 접근 정책을 실행 가능한 형태로 합의하는 일입니다.
