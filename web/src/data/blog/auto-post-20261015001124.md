## 실무 판단

이 모델의 주된 관심사는 파라미터 총량보다 추론 때 활성화되는 부분이 적은 구조와, 도구 사용 에이전트에 맞춘 공개 평가입니다. 다만 “활성 파라미터가 2B”라고 해서 2B 모델과 같은 저장 공간·메모리 요구량이 된다고 해석하면 안 됩니다. 전체 가중치 보관과 실제 실행에 필요한 메모리는 양자화 방식, 컨텍스트 길이, 실행 도구, 동시 요청 수 등에 따라 달라질 수 있습니다. 발표 발췌만으로는 특정 업무용 PC에서 요구되는 메모리나 모델별 다운로드 크기를 확정할 수 없습니다.

벤치마크 숫자도 도입 결정을 대신하지 않습니다. LiveClaw나 AutomationBench에서 점수가 높더라도 회사 내부의 브라우저 조작, 사내 문서 검색, 승인 절차가 같은 방식으로 동작한다고 보장하지 않습니다. 특히 에이전트는 답을 잘 쓰는 것 외에 올바른 도구 선택, 인자 형식, 권한 경계, 실패 후 중단 여부가 중요합니다. 제시된 결과를 후보 선정의 근거로 삼되, 실제 업무의 대표 작업을 이용한 자체 평가를 별도로 해야 합니다.

로컬 실행은 데이터가 외부 서비스로 전송되지 않도록 설계할 수 있다는 장점이 있지만, 모델을 기기에 설치했다는 사실만으로 데이터 보호가 완성되지는 않습니다. 로그, 도구 호출, 업데이트 절차, 사용자 접근 권한에 데이터가 남을 수 있습니다. 반대로 내부 장비에서 모델을 돌리면 용량·성능 관리와 장애 대응을 조직이 맡아야 합니다. 따라서 민감 정보가 많고 네트워크 제약이 있는 작업에는 로컬 실행을 검토할 이유가 있지만, 운영 역량과 기기 보유 현황을 함께 따져야 합니다.

## 업무에 어떻게 쓸까

첫 적용은 사람이 결과를 확인할 수 있고, 잘못 실행해도 되돌리기 쉬운 작업으로 한정합니다. 예를 들어 내부 문서의 핵심 항목 추출, 정해진 형식의 요약 초안, 읽기 전용 검색 도구를 사용하는 질의 응답처럼 성공·실패를 판정할 수 있는 과제가 적절합니다. 이는 도입 권고를 위한 예시이지, 해당 모델이 이 업무에서 검증됐다는 의미는 아닙니다.

1. **작업을 좁힙니다.** 팀에서 반복되는 과제 하나를 고르고 입력 예시와 기대 결과를 20~50건 정도 준비합니다. 개인정보나 비공개 자료가 들어가면 승인된 테스트 환경과 익명화 기준을 먼저 확인합니다.
2. **도구 권한을 제한합니다.** 첫 시험은 문서 읽기나 검색처럼 되돌리기 쉬운 도구만 연결합니다. 메일 발송, 파일 삭제, 결제, 외부 제출 등 실행 결과가 큰 도구는 붙이지 않거나 사람 승인 없이는 실행되지 않게 합니다.
3. **환경을 기록합니다.** 모델 버전, 양자화 파일, 실행 런타임, 장비, 입력 길이, 동시 실행 수를 남깁니다. 그래야 다른 환경에서 나온 속도 수치를 그대로 가져오지 않고, 자체 시험 결과를 재현할 수 있습니다.
4. **세 가지 결과를 측정합니다.** 정답 또는 업무 규칙 준수율, 도구 호출 성공률, 입력부터 완료까지의 시간을 기록합니다. 평균 속도뿐 아니라 느린 요청과 실패 사례도 따로 봅니다. 모델이 지어낸 값을 도구 결과로 포장하는지, 실패했을 때 멈추는지도 확인합니다.
5. **기준을 통과하면 제한적으로 확대합니다.** 사람이 검토한 뒤 업무에 반영하는 방식으로 시작하고, 작은 범위에서 일정 기간 결과를 축적합니다. 기존 방식보다 정확도나 처리 시간이 나아지지 않거나, 메모리·장애 대응 비용이 감당하기 어려우면 적용을 중단하고 다른 모델이나 API 방식과 비교합니다.

- [ ] 제한된 시범 운영 결과가 사전 기준에 미달하면 도입 확대를 보류한다.
