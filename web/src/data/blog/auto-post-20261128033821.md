## 업무에 어떻게 쓸까

새 기능이나 제품 아이디어를 검토할 때는 다음 순서로 작은 실험을 설계해 보세요.

1. **사용자와 작업을 한 문장으로 고정합니다.** “누가 어떤 반복 작업에서 막히는가?”를 씁니다. 특정 고객군이나 업무 흐름을 말할 수 없다면, 우선 제품 개발보다 문제 확인이 먼저입니다.
2. **기존 접점을 확인합니다.** 기존 제품 안에 진입점을 둘 수 있는지, 고객이 이미 쓰는 데이터나 배포 흐름과 연결되는지 살펴봅니다. 새 고객을 찾아야만 작동하는 아이디어라면, 그 유통 경로를 어떻게 검증할지도 별도 과제로 둡니다.
3. **제품 출시 전 운영 책임자를 지정합니다.** 문의 대응, 장애 대응, 접근 권한, 데이터 보관과 삭제, 보안 검토의 담당자를 정합니다. 담당자를 정할 수 없거나 필요한 통제를 확인할 수 없다면 출시 범위를 줄이거나 보류합니다.
4. **전체 제품이 아니라 가장 작은 사용 흐름을 시험합니다.** 기존 사용자가 실제 작업에서 기능을 발견하고, 결과를 확인하고, 다음 업무까지 이어가는지 관찰합니다. 클릭이나 생성 성공만으로 지속 사용을 입증했다고 보지 않습니다.
5. **계속·수정·중단 조건을 시작 전에 합의합니다.** 예를 들어 “기존 고객이 실제 업무에 반복 사용하고, 담당 팀이 지원과 보안 요구를 감당할 수 있으면 확장한다”처럼 정성 기준을 명시합니다. 사용자가 늘어도 운영 통제나 책임자가 준비되지 않았다면 확대를 중단합니다.

아래 템플릿을 기획 문서에 복사해 쓸 수 있습니다.

> - 대상 사용자와 작업:
> - 현재 불편과 확인 근거:
> - 기존 제품과의 연결 지점:
> - 시험할 최소 기능과 관찰할 행동:
> - 고객 지원·온콜 담당:
> - 데이터·보안·규제 검토 항목:
> - 계속할 조건:
> - 수정할 조건:
> - 즉시 중단할 조건:

초기 실험의 성공 기준은 기능이 생성됐다는 데 두지 말고, 사용자가 기존 업무 안에서 이를 선택하고, 운영팀이 감당 가능한 수준으로 지원할 수 있는지에 두는 것이 좋습니다. 이는 권고이며, 각 조직은 제품의 위험도와 자원에 맞춰 기준을 정해야 합니다.
