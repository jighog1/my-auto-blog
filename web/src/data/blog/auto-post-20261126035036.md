## 실무 판단

이 변화는 제품의 가치 평가 기준을 바꾸지만, 메뉴를 없애거나 모든 작업을 대화형으로 바꾸라는 뜻은 아닙니다. 메뉴와 버튼은 사용자가 직접 탐색하고 실행하는 데 유용합니다. 반면 반복적이고 명확한 작업은 자연어 요청을 받아 에이전트가 기능을 연결하는 편이 사용자에게 필요한 단계를 줄일 수 있습니다. 어떤 방식이 적합한지는 업무의 빈도, 오류 비용, 결과 확인 가능성에 따라 달라집니다. 이는 기사 내용에서 도출한 실무적 해석입니다.

기능 발견의 개선과 업무 위임의 개선도 따로 측정해야 합니다. 사용자가 기능을 더 자주 호출하게 됐다고 해서 원하는 결과를 정확히 얻었거나, 작업 시간을 줄였다고 단정할 수는 없습니다. 반대로 클릭 수가 줄어도 결과 검토와 수정에 시간이 더 들면 실질적인 개선은 아닐 수 있습니다. 도입 전후에는 기능 접근률뿐 아니라 완료율, 수정·취소 빈도, 사람의 검토 시간, 잘못된 실행의 영향 범위를 함께 살피는 편이 합리적입니다.

특히 외부 서비스에 쓰기 작업을 요청하는 에이전트는 발견 편의성과 권한 문제를 동시에 만듭니다. 조회와 초안 작성은 비교적 낮은 위험으로 시험할 수 있지만, 전송·삭제·승인처럼 외부에 영향을 주는 작업은 확인 단계를 두는 것이 안전합니다. 이는 제공된 자료에서 확인된 제품 동작이 아니라, 실행 권한을 제품 설계에 반영할 때의 권고입니다.

## 업무에 어떻게 쓸까

먼저 기능 목록이 아니라 업무의 출발점에서 후보를 찾습니다. 구성원이 자주 반복하는 요청을 몇 개 모아 “어떤 결과를 원했나”, “현재는 어느 앱에서 어떤 단계를 밟나”, “완료 여부를 누가 어떻게 확인하나”를 기록합니다. 요청이 모호하거나 매번 절차가 크게 달라지는 일은 초기 자동화 대상으로 삼지 않는 편이 좋습니다.

다음으로 후보 하나를 좁혀 현재 흐름과 에이전트 흐름을 나란히 적습니다. 예를 들어 보고서 초안 작성이라면 입력 자료, 참고해야 할 시스템, 산출물 형식, 사람이 확인할 항목을 정의합니다. 특정 제품의 기능 호출이나 연결이 실제로 가능한지는 이 자료만으로 확인할 수 없으므로, 개발 전에 해당 서비스의 API·권한·연동 범위를 별도로 검증해야 합니다.

초기 시험은 결과를 읽고 승인할 수 있는 업무부터 시작합니다. 요청을 받으면 에이전트가 어떤 자료를 읽고 어떤 기능을 호출했는지 표시하고, 실행 전 미리보기와 취소 경로를 제공합니다. 첫 단계부터 자동 전송이나 영구 삭제를 허용하지 말고, 결과 품질과 실패 유형을 확인한 뒤 권한을 넓힙니다. 아래 틀을 후보 업무마다 채우면 범위를 논의하기 쉽습니다.

| 기존 경로 | 사용 앱, 수행 단계, 반복되는 탐색 |

시험을 멈출 조건도 미리 정합니다. 승인 없이 외부에 결과가 나가거나, 잘못된 대상에 실행되거나, 실패를 사용자가 알아채기 어려운 상황이 발생하면 자동 실행을 중단하고 수동 승인으로 되돌립니다. 이 기준은 제품의 위험도에 맞춰 조정할 권고 사항입니다.
