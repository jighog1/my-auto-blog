## 30초 요약

- **Yap**은 AI가 생성한 코드에 붙은, 말은 많지만 코드를 이해하거나 유지보수하는 데 실질적인 도움이 적은 주석을 가리키는 표현입니다.
- 대표적인 모습은 단순한 타입 정의 위에 긴 설명을 덧붙이거나, 함수의 동작을 코드 한 줄씩 장황하게 되풀이하는 주석입니다.
- 문제는 주석의 길이 자체가 아니라 **새로운 정보가 있는지, 코드 가까이에 필요한 맥락을 제공하는지, 시간이 지나도 검증 가능한지**입니다.
- 리뷰에서는 `yap`을 짧은 요청어처럼 사용해 “이 주석이 가치를 주는가, 더 짧아질 수 있는가, 관련 코드 가까이에 있는가”를 다시 묻는 방식으로 활용할 수 있습니다.
- 오늘 바로 적용하려면 AI 생성 코드에서 주석만 먼저 모아 보고, 코드에 없는 정책·이유·제약을 설명하는 주석만 남기면 됩니다.

## 무슨 일인가

LLM(대규모 언어 모델)은 코드를 생성할 때 구현뿐 아니라 설명문과 주석도 함께 만드는 경우가 많습니다. 이때 설명이 충분하면 유지보수에 도움이 되지만, 설명이 코드의 내용을 단순히 되풀이하거나 실제 근거가 없는 서술로 길어지면 검토 대상이 됩니다. 입력 자료는 이런 특정 유형의 AI 생성 주석 슬롭을 **Yap**이라고 부릅니다.

Yap이라는 표현은 ‘yapping’이 끝난 뒤 남은 잔여물이라는 의미로 소개됩니다. 핵심은 문법이 틀렸다는 뜻이 아니라, **주석이 존재하지만 정보 밀도가 낮다**는 데 있습니다. 예를 들어 다음과 같은 주석은 코드가 이미 직접 보여주는 사실을 반복할 가능성이 큽니다.

```python
# 사용자의 이름을 저장하기 위한 문자열 타입의 변수입니다.
# 이 변수는 사용자 객체에서 이름 값을 가져와 할당됩니다.
# 문자열은 텍스트 데이터를 표현하는 데 사용됩니다.
user_name: str = user.name
```

이 주석은 길지만 `user_name`이 문자열이며 `user.name`을 할당한다는 사실 이상의 맥락을 거의 제공하지 않습니다. 반면 아래와 같은 주석은 코드만 보고 바로 알기 어려운 정책이나 제약을 기록할 수 있습니다.

```python
# 외부 결제 시스템의 고객명 제한이 40자이므로 전송 전에 자릅니다.
customer_name = customer.name[:40]
```

여기서 중요한 정보는 문자열을 자른다는 동작 자체가 아니라, **왜 40자인지**입니다. 해당 제한이 실제 외부 시스템의 규칙인지, 현재도 유효한지는 별도로 확인해야 하지만, 적어도 주석의 역할은 코드가 드러내지 않는 이유를 설명하는 데 있습니다.

다만 입력 자료만으로 Yap의 정식 표준, 자동 판별 도구, 특정 모델별 발생률이나 성능을 확인할 수는 없습니다. 따라서 이 글에서 Yap은 특정 도구의 공식 분류라기보다, AI가 생성한 코드의 장황하고 정보가 적은 주석을 검토하기 위한 실무적인 라벨로 다룹니다.

## 왜 중요한가

### 1. 코드 검토의 대상이 늘어난다

AI가 많은 코드를 만들어도 누군가는 그 코드를 읽고 검토해야 합니다. 이때 주석이 많으면 처음에는 친절해 보이지만, 검토자는 실제 변경점과 중요한 제약을 찾기 위해 불필요한 문장을 함께 읽어야 합니다. 즉, 코드의 양뿐 아니라 **읽어야 할 설명의 양**도 늘어날 수 있습니다.

특히 함수 위에 긴 설명이 붙어 있으면 핵심 동작, 예외 조건, 외부 의존성, 보안상 주의점을 찾는 데 시간이 더 걸릴 수 있습니다. 이것은 “긴 주석은 항상 나쁘다”는 뜻이 아닙니다. 길이에 비해 새로운 정보가 적을 때 리뷰 비용이 커진다는 의미입니다.

### 2. 주석이 코드보다 빨리 낡을 수 있다

코드가 바뀌었는데 주석이 그대로 남으면, 주석은 문서가 아니라 오해의 원인이 됩니다. AI가 생성한 설명은 자신 있게 작성되어 있어도 프로젝트의 실제 정책이나 외부 시스템의 제약을 확인했다는 보장은 입력 자료에 없습니다. 따라서 주석이 그럴듯하다는 이유만으로 사실로 취급해서는 안 됩니다.

실무에서 주석은 다음 질문에 답할 때 가치가 커집니다.

- 코드만 읽어서는 알기 어려운 **이유**가 있는가?
- 외부 시스템, 규정, 호환성처럼 코드 밖의 **제약**을 기록하는가?
- 실패 시 동작, 데이터 손실 방지, 보안 경계처럼 놓치면 위험한 **주의점**을 알려주는가?
- 시간이 지나도 확인할 수 있는 근거 또는 변경 시 함께 갱신할 대상이 있는가?

### 3. 설명의 양과 신뢰성을 혼동하기 쉽다

장황한 문장은 상세해 보이지만, 상세함과 정확성은 다릅니다. 주석이 코드의 모든 줄을 다시 설명해도 그 내용이 프로젝트의 실제 동작을 검증해 주지는 않습니다. 반대로 짧은 한 줄이라도 “이 검사는 중복 결제를 막기 위한 것”처럼 설계 의도를 정확히 남기면 더 유용할 수 있습니다.

입력 자료에는 LLM이 존재하지 않는 패키지 이름을 출력하고 사용자가 이를 설치할 수 있는 위험을 설명하는 **slopsquatting** 사례도 함께 제시됩니다. 이는 Yap과 같은 현상을 직접 설명하는 자료는 아니지만, AI 출력이 자연스럽고 그럴듯해 보여도 사람이 사실 여부와 사용 가능성을 확인해야 한다는 인접한 주의점으로 볼 수 있습니다. 주석뿐 아니라 패키지명, API 사용법, 설정값도 그대로 신뢰하지 않는 검토 습관이 필요합니다.

## 업무에 어떻게 쓸까

### 1단계: AI 생성 코드의 주석을 별도로 모은다

처음부터 모든 주석을 삭제하지 말고, 변경된 파일에서 새로 생긴 주석만 확인합니다. 코드 리뷰 도구나 에디터의 검색 기능으로 다음 패턴을 찾아도 됩니다.

- `#`, `//`, `/* ... */` 등 프로젝트 언어의 주석
- 함수·클래스·타입 정의 바로 위의 여러 줄 설명
- `TODO`, `NOTE`, `IMPORTANT`처럼 주의를 끄는 표식
- “이 함수는”, “이 변수는”, “이 클래스는”으로 시작하며 코드 동작을 반복하는 문장

이 단계의 목적은 AI를 탓하는 것이 아니라, **주석이 변경의 일부로 들어왔다는 사실을 가시화하는 것**입니다. 사람이 작성한 주석도 같은 기준으로 검토해야 일관성이 생깁니다.

### 2단계: 각 주석을 세 가지 질문으로 판정한다

각 주석에 다음 질문을 적용합니다.

1. **새로운 정보가 있는가?** 코드에 그대로 적힌 동작을 반복하지 않고 이유, 제약, 위험, 외부 맥락을 설명하는가?
2. **더 짧게 쓸 수 있는가?** 같은 의미를 한두 문장으로 줄여도 독자가 판단하는 데 문제가 없는가?
3. **관련 코드 가까이에 있는가?** 설명 대상과 멀리 떨어져 있거나, 여러 구현을 한꺼번에 설명해 오히려 범위를 흐리지 않는가?

세 질문에 모두 부정적이면 삭제 후보입니다. 하나라도 긍정적이면 주석을 남기되, 어떤 사실을 전달하는지 한 문장으로 다시 써 봅니다. 이때 리뷰 댓글에 `yap`이라고 적고 위 세 질문을 다시 적용하는 방식도 사용할 수 있습니다. 입력 자료에서 이 표현은 주석이 가치를 주는지, 더 짧아야 하는지, 관련 코드 가까이에 있는지 묻는 한 단어 요청으로 소개됩니다.

### 3단계: 주석을 정보 유형별로 다시 쓴다

주석을 남길 때는 다음 템플릿 중 하나를 선택하면 장황함을 줄이기 쉽습니다.

```text
# 이유: [왜 이 처리가 필요한가]
# 제약: [외부 시스템·정책·호환성 조건은 무엇인가]
# 위험: [이 처리를 바꾸면 어떤 문제가 생길 수 있는가]
# 예외: [일반적인 흐름과 다른 입력 또는 실패 조건은 무엇인가]
```

예를 들어 “이 함수는 목록을 순회하면서 각 항목을 처리합니다”처럼 코드가 이미 보여주는 문장은 제거할 수 있습니다. 대신 “이 목록은 순서가 보존되어야 하므로 집합으로 바꾸지 않는다”처럼 구현 선택의 이유를 남길 수 있습니다. 단, 그 이유가 실제 요구사항인지 확인되지 않았다면 단정적으로 기록하지 말고 담당자나 관련 문서와 대조해야 합니다.

### 4단계: 주석을 삭제하기 전에 코드 구조를 개선한다

주석이 코드의 복잡한 동작을 장황하게 설명하고 있다면, 단순 삭제가 항상 해결책은 아닙니다. 다음 순서로 판단합니다.

- 이름만으로 의도가 드러나지 않으면 변수·함수 이름을 개선합니다.
- 한 함수가 여러 작업을 수행하면 작은 함수로 나눌 수 있는지 봅니다.
- 반복되는 설명이 있다면 공통 함수나 명확한 자료구조로 표현할 수 있는지 확인합니다.
- 코드만으로 표현하기 어려운 정책이나 외부 제약만 짧은 주석으로 남깁니다.

이렇게 하면 주석을 문서로 과도하게 사용하지 않고, 코드 자체의 읽기 가능성을 높일 수 있습니다. 다만 실제 리팩터링이 변경 범위를 키울 수 있으므로, 긴급 수정이나 작은 패치에서는 주석 정리만 먼저 하고 구조 변경은 별도 작업으로 분리하는 편이 안전합니다.

### 5단계: 커밋 전 체크리스트로 고정한다

팀의 AI 코드 리뷰나 커밋 전 점검에 다음 항목을 추가할 수 있습니다.

```text
[ ] 새 주석이 코드의 동작을 단순히 반복하지 않는가?
[ ] 주석이 설명하는 이유·제약·위험을 확인할 근거가 있는가?
[ ] 두세 문장으로 줄여도 의미가 유지되는가?
[ ] 주석이 설명 대상 코드 바로 근처에 있는가?
[ ] 코드가 바뀔 때 함께 갱신해야 할 주석인가?
[ ] 존재하지 않는 패키지·API·설정을 사실처럼 전제하지 않는가?
```

적용 조건은 간단합니다. AI가 코드와 주석을 함께 생성하는 팀, 코드 리뷰 시간이 길어지는 프로젝트, 외부 API나 정책 제약이 많은 코드베이스에서 특히 유용합니다. 반대로 주석 스타일과 갱신 책임이 이미 명확한 프로젝트라면 기존 규칙에 Yap 점검을 추가하는 정도로 시작하면 됩니다.

## 한계와 주의점

### Yap 여부를 길이만으로 판정하지 않는다

짧은 주석도 틀릴 수 있고, 긴 주석도 꼭 필요할 수 있습니다. 복잡한 알고리즘의 불변식, 법적·보안상 제약, 장애 대응 절차처럼 코드만으로 표현하기 어려운 내용은 여러 문장이 필요할 수 있습니다. 따라서 글자 수나 줄 수를 자동 기준으로 삼기보다, 독자가 어떤 결정을 내리는 데 필요한 정보를 제공하는지 확인해야 합니다.

### 삭제 전에 사실과 책임자를 확인한다

주석이 불필요해 보여도 그 안에 숨은 정책이 있을 수 있습니다. 삭제하기 전에 관련 테스트, 설계 문서, 외부 시스템 문서 또는 해당 코드를 관리하는 담당자에게 확인합니다. 입력 자료는 개별 주석의 정확성을 검증하는 방법이나 특정 조직의 승인 절차를 제공하지 않으므로, 이 부분은 팀의 개발 프로세스로 보완해야 합니다.

### AI가 쓴 설명을 검증된 사실로 보지 않는다

입력 자료만으로 특정 LLM, 코딩 도구, 언어별 플러그인, 자동 Yap 탐지기의 지원 여부나 성능은 확인할 수 없습니다. 따라서 “어떤 모델은 반드시 Yap을 만든다”거나 “특정 도구가 이를 완벽하게 제거한다”고 단정해서는 안 됩니다. 도구를 도입한다면 실제 저장소의 변경 이력으로 오탐과 누락을 먼저 평가해야 합니다.

또한 slopsquatting 자료가 보여주는 것은 존재하지 않는 패키지 이름을 AI가 출력할 수 있고 사용자가 이를 설치할 수 있다는 위험입니다. 이것을 Yap과 동일한 문제라고 확대해서는 안 되지만, AI가 생성한 주석과 코드의 주변 정보까지 사람이 확인해야 한다는 보안 원칙은 함께 적용할 수 있습니다. 패키지 설치, 권한 부여, 외부 API 호출처럼 되돌리기 어려운 작업은 특히 이름과 동작을 별도로 검증합니다.

### 팀 규칙은 “주석 최소화”보다 “정보 밀도”에 둔다

모든 주석을 없애면 코드 밖의 중요한 이유와 제약도 사라질 수 있습니다. 권장할 기준은 주석의 개수가 아니라 다음과 같습니다.

- 코드가 말하지 못하는 정보를 남긴다.
- 짧고 구체적으로 쓴다.
- 변경될 가능성이 높은 사실은 근거와 함께 관리한다.
- 주석이 오래되어 틀릴 위험이 있으면 테스트나 명확한 코드 구조로 대체한다.

결국 Yap을 줄이는 핵심은 AI 생성물을 무조건 믿거나 무조건 지우는 것이 아닙니다. 주석 하나가 리뷰어에게 새로운 판단 근거를 주는지 확인하고, 그렇지 않으면 더 짧게 쓰거나 코드로 의도를 드러내는 습관을 만드는 것입니다.
