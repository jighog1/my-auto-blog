## 30초 요약

AI 기능을 개선할 때 먼저 정할 것은 점수 자체가 아니라 무엇이 실패인지입니다. 실제 사용 기록에서 반복되는 문제를 찾고, 이를 평가 기준과 테스트 사례로 바꿔야 모델이나 프롬프트를 변경한 뒤에도 개선 여부를 비교할 수 있습니다. 업무 적용의 핵심은 작게 시작하는 것입니다. 실패 유형 몇 가지를 선정하고, 코드로 확인할 수 있는 항목부터 자동화한 뒤, 검색·생성·도구 사용처럼 결과를 만드는 각 단계를 나눠 살펴보세요.

평가 점수 하나만으로는 안정성, 비용, 응답 시간까지 판단하기 어렵습니다. 특히 같은 입력에서도 결과가 달라질 수 있는 AI 기능이라면 반복 실행 결과와 실패 사례를 함께 추적해야 합니다.

## 실무 판단

여기서 얻을 수 있는 실무적 결론은 평가를 최종 점수 산출 작업으로만 두지 않는 것입니다. 평가 데이터는 어떤 실패를 줄이려는지에 대한 기록이자, 변경 전후 결과를 비교하는 기준입니다. 따라서 데이터셋의 사례와 기준이 현재 업무의 위험을 반영하는지부터 점검해야 합니다. 과거에 잘 답했던 쉬운 질문만 많이 모으면, 중요한 경계 사례의 퇴보를 놓칠 수 있습니다.

첫 평가 지표는 넓고 추상적인 ‘답변 품질’보다 관찰 가능한 실패 유형에 맞추는 편이 유용합니다. 예를 들어 사내 문서 검색 기능이라면 ‘근거가 없는 주장을 한다’와 ‘관련 문서를 찾지 못한다’를 구분할 수 있습니다. 두 문제를 하나의 점수로 합치면 검색 개선이 필요한지, 답변 생성 개선이 필요한지 판단하기 어려워집니다. 이는 원문에서 제시한 검색·생성 분리 원칙을 업무 문제에 적용한 해석입니다.

반복 실행 신뢰성도 별도 판단 항목으로 두는 것이 좋습니다. 한 번의 성공은 간헐적 실패가 없다는 뜻이 아닙니다. 따라서 업무상 매번 안정적인 결과가 중요한 기능과, 여러 번 시도하면 되는 탐색형 기능은 같은 합격 기준을 쓰지 않아야 합니다. pass@k가 높은 경우에도 pass^k가 낮을 수 있다는 점을 운영 요구사항과 연결해 보세요.

평가를 시작할 때부터 모든 항목을 자동화할 필요는 없습니다. 형식이나 필수 항목처럼 규칙이 명확한 것은 코드로 먼저 검사하고, 맥락 적합성처럼 정답 규칙을 명시하기 어려운 것은 사람 검토나 모델 기반 평가를 보조적으로 활용할 수 있습니다. 다만 평가자나 평가 모델의 판정도 오류가 날 수 있으므로, 중요한 변경은 원본 사례를 직접 확인할 수 있어야 합니다.

## 업무에 어떻게 쓸까

적용 대상은 업무에서 반복 실행되는 AI 기능으로 좁히는 것이 좋습니다. 예를 들면 사내 문서 질의응답, 분류·요약, 코드 생성, 업무 시스템을 조작하는 에이전트입니다. 다음 순서로 작은 평가 묶음을 만드세요.

1. **실패 기록을 모읍니다.** 실제 운영이 있다면 최근 실행 기록에서 실패로 보이는 사례를 추립니다. 100건 이상을 살펴보는 것은 원문이 제안한 출발점이지, 모든 팀에 적용해야 하는 고정 요건은 아닙니다. 기록이 적다면 현재 확보한 사례부터 분류하고, 사용이 늘면서 보완합니다.
2. **실패를 짧은 이름으로 나눕니다.** 예: 근거 누락, 필수 정보 누락, 잘못된 도구 선택, 형식 오류. 사례마다 한 가지 주된 원인을 우선 기록하고, 원인이 불분명하면 ‘판정 보류’로 남깁니다. 억지로 한 범주에 넣지 않는 편이 데이터의 왜곡을 줄입니다.
3. **각 사례에 합격 조건을 씁니다.** 정답 문장이 하나로 정해지지 않는 업무라면 기대 출력 대신 확인 가능한 기준을 둡니다. 예: ‘답변의 핵심 주장이 제공된 문서에 근거해야 함’, ‘요청한 필수 항목을 모두 포함해야 함’. 판정자가 달라져도 같은 판단을 할 수 있는지 동료와 몇 건을 함께 검토합니다.
4. **검사 가능한 것부터 실행합니다.** JSON 스키마, 필수 키, 길이 범위, 테스트 환경에서의 실행 여부처럼 규칙이 분명한 항목을 자동화합니다. 그다음 의미 평가가 필요한 항목을 별도 묶음으로 둡니다. RAG라면 검색 결과와 생성 답변의 사례·점수를 따로 기록합니다.
5. **변경 전후를 같은 데이터로 비교합니다.** 모델, 프롬프트, 검색 설정 중 무엇을 바꿨는지 기록하고, 기존 사례와 새로 추가한 사례를 구분합니다. 새 사례만으로 점수가 좋아졌다고 판단하지 않도록 이전 기준 데이터도 함께 실행합니다.
6. **운영 적용 여부를 조건으로 정합니다.** 중요한 실패 유형이 악화되거나, 반복 실행에서 허용할 수 없는 변동이 나타나면 배포를 보류하고 원인을 확인합니다. 품질이 좋아져도 비용이나 지연 시간이 업무 한도를 넘으면 적용을 중단하거나 범위를 줄입니다. 이 기준은 각 조직이 사전에 정해야 할 운영 판단입니다.

바로 재사용할 수 있는 사례 기록 양식입니다.

| 항목 | 기록 내용 |
|---|---|
| 사례 ID / 버전 | 고유 ID, 데이터셋·프롬프트 버전 |
| 입력과 맥락 | 사용자 입력, 검색 자료 또는 필요한 메타데이터 |
| 실패 유형 | 근거 누락, 형식 오류 등 분류명 |
| 합격 기준 | 사람이 확인할 수 있는 구체적 조건 |
| 실행 결과 | 출력, 도구 호출 경로, 실행 횟수 |
| 판정과 후속 조치 | 통과 여부, 원인, 재검토 담당 |

처음에는 상위 실패 유형 몇 개와 소규모 사례 묶음만으로도 변경 효과를 논의할 수 있습니다. 단, 그 결과를 전체 사용자나 모든 입력 조건으로 일반화하지 말고, 테스트한 범위 안에서만 해석하세요.

## 한계와 주의점

원문 발췌와 허용된 자료만으로는 특정 평가 프레임워크, 도구, 데이터 저장 방식이나 CI 시스템의 구현 방법을 확인할 수 없습니다. 따라서 여기서 제안한 기록 양식과 적용 순서는 도입을 위한 편집부 권고이지, 특정 제품을 사용해 검증한 절차가 아닙니다. 운영 데이터에 개인 정보나 민감한 업무 정보가 포함되는 경우에는 수집·보관·검토 권한도 별도로 확인해야 합니다.

100개 이상 표본, 실패 유형의 빈도, pass@k·pass^k 같은 제안은 평가를 구조화하기 위한 출발점입니다. 표본이 실제 사용자와 입력 난도를 대표하는지, 테스트 사례가 최신 업무 규칙을 반영하는지 확인하지 않으면 점수가 실제 품질을 대변하지 않을 수 있습니다. 희귀하지만 영향이 큰 실패는 빈도가 낮다는 이유로 평가에서 빠지지 않도록 별도로 관리해야 합니다.

모델 기반 평가를 사용할 때는 평가 기준의 모호함, 판정의 일관성, 사람의 검토 결과와의 차이를 점검해야 합니다. 특히 단일 점수만으로 출시 여부를 결정하면 특정 실패의 악화가 평균에 가려질 수 있습니다. 평가 결과는 적용 범위와 한계를 함께 기록하고, 실제 업무에서 새로 발견된 실패가 테스트와 합격 기준을 갱신하는 경로를 마련하는 것이 중요합니다.
