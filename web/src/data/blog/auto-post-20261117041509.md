## 실무 판단

이 도구의 실무적 의미는 에이전트가 웹을 ‘볼 수 있다’는 데 그치지 않습니다. 사용자가 이미 로그인한 브라우저에 접근하면 별도 로그인 절차를 반복하지 않아도 되지만, 브라우저에 보이는 정보와 계정 권한이 작업의 일부가 됩니다. 따라서 편의성은 접근 범위가 넓어지는 만큼의 관리 책임과 함께 평가해야 합니다. 이는 제품 소개에 나온 기존 로그인 상태 활용과 사이트 제한 기능에서 도출할 수 있는 판단입니다.

적합한 첫 후보는 결과를 사람이 확인하기 쉽고, 잘못된 동작이 되돌릴 수 있는 업무입니다. 예를 들면 사내 승인된 웹페이지에서 특정 정보를 찾아 요약하거나, 테스트 환경의 화면을 확인하고, 비파괴적인 양식 입력을 준비하는 작업입니다. 반대로 실제 고객에게 메시지를 보내거나, 데이터를 삭제·게시하거나, 결제를 확정하는 업무는 ‘클릭이 가능하다’는 이유만으로 자동화를 허용하기 어렵습니다. 이는 기능의 한계에 대한 주장이 아니라, 영향이 큰 행동에 사람의 확인을 두자는 운영 권고입니다.

사이트 허용 목록은 편의 설정이 아니라 에이전트 작업 범위를 정하는 정책으로 다루는 것이 좋습니다. 업무에 필요한 도메인만 지정하고, 작업이 끝나면 범위를 넓힌 채 방치하지 않는 방식입니다. 특히 기존 로그인 상태를 활용하므로 개인 브라우저 전체를 무심코 연결하기보다, 업무용 프로필이나 별도 계정에서 시험하는 방안을 검토할 수 있습니다. 다만 제공된 자료만으로 프로필 격리나 조직 차원의 정책 기능이 어느 수준까지 제공되는지는 확인되지 않으므로, 이를 제품 기능으로 전제해서는 안 됩니다.

또 하나의 판단 기준은 관찰 가능성입니다. 스크린샷과 녹화, 네트워크 트래픽 캡처가 제공된다는 점은 작업 결과를 검토하는 데 쓸 수 있습니다. 그러나 캡처가 어떤 정보를 저장하는지, 어디에 보관되는지, 누가 볼 수 있는지는 소개 자료만으로 확인할 수 없습니다. 따라서 캡처 기능을 켜기 전에 민감정보가 화면이나 요청에 포함될 가능성과 보관·공유 방식을 별도로 확인해야 합니다.

## 업무에 어떻게 쓸까

첫 시험은 운영 데이터가 아닌 테스트 환경에서, 한 가지 목적만 정해 진행합니다. 예를 들어 “허용된 테스트 사이트의 특정 페이지에서 상태값을 확인하고 요약한다”처럼 결과가 읽기 중심인 작업을 고릅니다. 작업 전후의 상태를 비교할 수 있어야 하고, 잘못된 클릭이 실제 고객·비용·계정 권한에 영향을 주는 과제는 초기 시험에서 제외합니다.

1. **대상과 결과를 한 문장으로 정합니다.** 어떤 사이트에서 무엇을 확인할지, 에이전트가 해도 되는 동작이 읽기인지 입력까지인지 명시합니다. ‘사이트를 알아서 처리해’처럼 목적과 경계가 열려 있는 요청은 시험 과제로 삼지 않습니다.
2. **허용 사이트를 최소 범위로 설정합니다.** 해당 작업에 필요한 사이트만 허용하고, 브라우저에 열려 있는 다른 업무·개인 탭을 작업에 넘기지 않습니다. 허용 목록 설정이 실제로 의도한 도메인에 적용되는지 먼저 확인합니다.
3. **낮은 영향의 동작부터 확인합니다.** 페이지 읽기와 화면 확인을 먼저 수행한 뒤, 테스트용 양식의 입력처럼 되돌릴 수 있는 동작으로 확대합니다. 클릭이 제출·저장·삭제를 의미하는 화면에서는 다음 단계로 진행하지 말고 사람이 직접 검토하도록 합니다.
4. **사람이 이어받는 지점을 시험합니다.** 로그인, 2FA, 결제 등 사용자 작업이 필요한 흐름에서 탭이 사용자에게 넘어오는지, Continue를 누르기 전후에 어떤 동작이 진행되는지 확인합니다. 이 인계가 기대와 다르면 실제 계정이나 운영 작업에 적용하지 않습니다.
5. **증거와 결과를 함께 검토합니다.** 에이전트의 요약만으로 성공을 판단하지 말고 화면 상태와 작업 결과를 대조합니다. 캡처 자료에 민감정보가 포함되는지, 필요 이상으로 남는 자료가 있는지 확인한 뒤 기록 방식을 정합니다.
6. **중단 조건을 미리 정합니다.** 허용되지 않은 페이지로 이동하거나, 예상 밖의 확인창·권한 요청이 나타나거나, 작업 결과를 되돌릴 수 없다고 판단되면 즉시 중단합니다. 에이전트가 같은 동작을 반복하거나 현재 상태를 설명하지 못하는 경우도 사람에게 넘길 기준으로 둡니다.
