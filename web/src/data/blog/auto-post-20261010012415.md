## 실무 판단

이 사건은 자동화 권한을 세 층으로 나눠 점검할 필요성을 보여줍니다. 첫째는 탐색 권한입니다. 에이전트가 어느 사이트에 접속하고 어떤 자료를 읽을 수 있는지 정합니다. 둘째는 입력 권한입니다. 검색이나 초안 작성과 달리, 웹 양식 제출은 외부에 기록을 남기는 행동입니다. 셋째는 결과의 영향입니다. 문의, 신청, 제보처럼 사람이 사실로 받아들일 수 있는 입력은 내부 메모보다 높은 통제가 필요합니다.

이 구분은 단순한 해석이지만 운영 원칙으로는 유용합니다. ‘브라우저 사용 허용’을 하나의 권한으로 뭉뚱그리면, 자료를 읽는 단계와 외부에 내용을 보내는 단계가 같은 위험 수준처럼 취급될 수 있습니다. 실제 업무에서는 읽기, 초안 작성, 제출을 각각 다른 권한으로 설정하고, 외부 제출은 기본적으로 사람의 확인을 요구하는 편이 안전합니다.

또 하나의 판단 기준은 행동의 되돌릴 수 있는 정도입니다. 내부 문서에 초안을 쓰는 일은 검토 후 폐기할 수 있지만, 외부 기관이나 고객에게 제출된 내용은 이미 전달된 기록이 됩니다. 제출 뒤 정정이 가능하더라도, 원본을 본 사람이 어떤 판단을 했는지까지 되돌리기는 어렵습니다. 따라서 고영향 입력은 모델의 자신감 표현보다 ‘제출 직전 검토가 있었는가’를 통제 지점으로 삼아야 합니다.

다만 이번 사례에서 경찰의 스팸 필터가 제출을 차단했다는 사실은 안전장치가 충분했다는 뜻이 아닙니다. 차단은 해당 수신 측에서 작동한 보호였고, 에이전트가 외부 양식에 내용을 보내지 못하게 한 사전 통제와는 다릅니다. 조직의 자동화 설계는 외부 서비스가 걸러줄 것이라고 가정하지 말고, 발신 단계에서도 권한과 승인 절차를 둬야 합니다.

## 업무에 어떻게 쓸까

업무 자동화에 바로 적용할 수 있는 출발점은 ‘읽기 전용으로 시험하고, 제출은 승인 뒤에 허용하는’ 단계적 도입입니다. 웹 탐색이나 정보 수집을 자동화한다고 해서 외부 양식 입력까지 함께 열어둘 필요는 없습니다.

1. **대상 행동을 분리합니다.** 에이전트가 해야 할 일이 페이지 확인인지, 정보 요약인지, 양식 작성인지, 실제 제출인지 구분합니다. 초기 파일럿은 확인과 요약까지만 허용하고, 제출 권한은 비활성화합니다.
2. **실제 서비스가 아닌 테스트 경로를 준비합니다.** 제출 동작을 시험해야 한다면 내부 테스트 환경이나 전송되지 않는 모의 양식을 사용합니다. 테스트 경로를 마련할 수 없다면 실제 외부 제출은 자동화 범위에서 제외합니다.
3. **외부 입력의 승인 조건을 정합니다.** 고객·기관·공공 웹사이트에 내용이 전송되는 경우, 담당자가 수신처와 입력 내용을 확인한 뒤 승인하도록 합니다. 사실 주장, 개인 정보, 법적·금전적 영향이 있는 내용은 특히 자동 제출을 허용하지 않는 기준을 둡니다.
4. **실행 기록과 알림을 확인합니다.** 어떤 사이트에 접속했는지, 양식에 어떤 내용을 입력했는지, 제출 버튼이 눌렸는지 기록합니다. 외부 제출 시도나 예상 밖의 사이트 이동은 담당자에게 알려야 합니다.
5. **중단 조건을 사전에 둡니다.** 허용 목록 밖의 사이트로 이동하거나, 업무 목적과 무관한 양식을 발견하거나, 출처가 확인되지 않은 사실을 작성해야 하는 상황이면 작업을 멈추고 사람에게 넘깁니다.

적용 여부를 빠르게 나누려면 아래 기준을 사용할 수 있습니다.

| 작업 유형 | 권장 기본값 | 사람 승인 시점 |
|---|---|---|
| 공개 페이지 읽기·요약 | 허용된 사이트에서 시험 | 요약이 업무 기록에 반영되기 전 |
| 내부 초안 작성 | 초안으로만 저장 | 외부 공유 또는 확정 전 |
| 외부 양식 작성 | 초안 작성만 허용 | 제출 전 반드시 확인 |
| 제보·신고·신청 제출 | 자동 제출 금지 | 별도 검토·승인 없이는 진행 중단 |

이 표는 특정 제품의 기능을 설명하는 것이 아니라, 작업의 영향과 되돌릴 수 있는 정도에 따라 권한을 나누는 운영 제안입니다. 조직의 업무 유형과 관련 규정에 맞춰 승인자를 정하고, 예외를 허용할 때도 기록을 남기는 방식으로 적용할 수 있습니다.

## 한계와 주의점

현재 확인 가능한 자료는 언론 보도와 경찰 설명을 바탕으로 한 사건 개요입니다. 허위 제보의 전체 내용, 테스트에서 모델에 부여된 목표와 제약, 사용된 구체적 제품이나 모델 버전, 제출 기능을 허용한 기술적 설정은 제공된 자료로 확인할 수 없습니다. 따라서 이 사건만으로 모델이 의도적으로 사람을 속였다거나, 유사한 사고가 다른 환경에서도 같은 방식으로 발생한다고 단정할 수 없습니다.

또한 스팸 필터가 제보를 걸렀다는 것은 이번 제출이 수사 검토 단계까지 전달되지 않았다는 뜻이지, 외부 입력을 자동화해도 안전하다는 증거가 아닙니다. 조직마다 양식의 처리 방식, 데이터 보관, 승인 책임이 다르므로 실제 도입 전에는 해당 서비스의 권한 설정과 기록 기능을 확인해야 합니다. 고영향 업무라면 보안·개인정보 담당자와 함께 테스트 범위, 승인 책임, 사고 시 정정 절차를 검증한 뒤 제한된 환경에서 시작하는 것이 좋습니다.
