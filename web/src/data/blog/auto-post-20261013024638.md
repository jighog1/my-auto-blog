## 실무 판단

위 사례를 묶으면 실패 원인은 네 가지 운영 질문으로 정리할 수 있습니다. 첫째, 완료를 누가 어떤 증거로 판단하는가. 둘째, 여러 CLI가 같은 규칙을 읽는가. 셋째, 도구가 할 수 있는 일과 승인 없이 할 수 있는 일이 구분돼 있는가. 넷째, 실패나 응답 지연 뒤에 같은 작업을 다시 실행해도 안전한가. 이는 소개된 항목에서 도출한 편집부의 해석입니다.

따라서 “에이전트가 일을 많이 했는가”보다 “검증 가능한 산출물을 남겼는가”를 운영 지표로 삼는 편이 유용합니다. 예를 들어 테스트 실행 결과, 변경 파일 목록, 외부 시스템 처리 여부가 보고되지 않았다면 작업 완료로 처리하지 않는 기준을 둘 수 있습니다. 다만 모든 작업에 같은 강도의 검증을 요구할 필요는 없습니다. 문서 초안과 배포, 데이터 변경은 실패 비용이 다르므로 권한과 검증 수준을 작업 위험도에 맞춰야 합니다.

세 번 재시도 규칙도 무조건 적용할 숫자라기보다, 수정이 끝없이 이어지는 상황을 끊는 기준으로 보는 편이 적절합니다. 실패 유형이 매번 다르고 안전하게 되돌릴 수 있는 작업이라면 담당자가 추가 시도를 승인할 수 있습니다. 반대로 같은 테스트가 반복해서 실패하거나 변경 범위가 넓어지면, 더 시도하기보다 원인과 현재 상태를 보고하도록 멈추는 것이 낫습니다. 이 판단은 소개 글의 제안을 실제 팀 절차에 적용하기 위한 권고입니다.

특히 “응답 없음”과 “처리되지 않음”은 같은 뜻이 아닙니다. 외부 요청을 보낸 뒤 응답만 유실됐을 수 있으므로, 확인 없이 다시 보내면 중복 처리 위험이 생깁니다. 결제·배포·티켓 생성처럼 외부 상태를 바꾸는 작업은 코드 편집과 별도의 재시도 정책을 두는 것이 좋습니다. 소개 글은 멱등성 키와 `unknown` 상태를 제안하지만, 각 시스템의 지원 여부는 별도 확인이 필요합니다. [GeekNews 소개](https://news.hada.io/topic?id=35266)

## 업무에 어떻게 쓸까

**적용 조건:** 저장소에 테스트 명령이 있고, 에이전트가 파일을 수정하거나 명령을 실행하며, 결과를 사람이 검토하는 작업부터 시작합니다. 처음부터 모든 프로젝트에 적용하기보다 한 저장소와 한 종류의 작업을 골라 규칙이 실제 흐름에 맞는지 확인합니다.

1. **작업 완료 형식을 고정합니다.** 요청서나 에이전트 지침에 변경 내용, 수정한 파일, 실행한 검증 명령, 실제 결과, 실행하지 못한 검증, 남은 위험을 적도록 합니다. 결과를 확인하지 못한 항목은 통과로 보고하지 않게 합니다.
2. **공통 지침의 기준 파일을 정합니다.** 저장소 루트에 공통 규칙을 두고, 각 CLI의 설정이 그 파일을 읽는지 확인합니다. 도구별로만 필요한 내용은 별도 섹션에 구분하고, 서로 다른 규칙이 생기면 담당자가 어느 쪽을 기준으로 삼을지 결정합니다.
3. **권한을 작업별로 나눕니다.** 읽기·검색, 파일 편집, 테스트 실행, 외부 시스템 변경을 같은 권한으로 취급하지 않습니다. 리뷰 역할에는 기본적으로 수정 권한을 주지 않는 방안을 검토하고, 위험 명령 차단 규칙은 훅이나 권한 설정으로 구현한 뒤 차단 동작을 시험합니다.
4. **실패 시 멈추는 규칙을 만듭니다.** 같은 문제를 반복 수정하거나 테스트를 우회하는 징후가 나타나면 중단하고, 시도한 내용과 실패 로그를 사람에게 넘기도록 합니다. 재시도 횟수는 소개 글의 세 번을 시작점으로 삼을 수 있지만, 프로젝트 위험도에 따라 조정합니다.
5. **외부 작업은 별도 절차를 둡니다.** API 호출이나 배포처럼 외부 상태가 변하는 작업은 요청 식별자, 현재 처리 상태, 재전송 전 확인 절차를 정합니다. 상대 시스템에서 상태를 확인할 방법이 없으면 자동 재시도를 중단하고 담당자 확인으로 전환합니다.

복사해 쓸 수 있는 완료 보고 형식은 다음과 같습니다.

```text
변경 요약:
수정 파일:
실행한 검증 명령:
실제 결과:
실행하지 못한 검증과 이유:
재시도 횟수:
외부 시스템 처리 상태: 완료 / 미완료 / 확인 불가
남은 위험 또는 다음 조치:
```

여기서 핵심은 양식 자체보다 빈칸을 허용하는 방식입니다. 검증을 실행하지 못했다면 이유를 적고, 외부 작업 상태를 확인하지 못했다면 “확인 불가”로 남겨야 합니다. 이를 통해 확인되지 않은 성공 보고와 응답 지연 뒤의 무분별한 재실행을 구분할 수 있습니다.
